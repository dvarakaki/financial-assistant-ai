Por que isso é um problema

No script isso não podia acontecer: input() sempre devolve uma string, sempre presente. Na web chega um JSON qualquer, montado por alguém que você não controla — pode vir sem campo, com tipo errado, ou vazio. E o /docs não sabe dizer qual é o formato esperado, porque você também não disse.

app/schemas.py Objetivo: definir o formato exato do que entra e do que sai.

Não existia nada equivalente — não havia o que validar num script onde a entrada vinha do teclado. Agora, como classes Pydantic, o FastAPI usa isso para três coisas de uma vez: validar o que chega, converter a resposta em JSON e gerar o /docs.

app/schemas.py
pythonClique para ver o código
from pydantic import BaseModel, Field class ChatRequest(BaseModel): """O que o navegador envia no POST /chat.""" session_id: str = Field(..., examples=["id_usuario"]) pergunta: str = Field(..., min_length=1, examples=["gastei 50 reais no mercado"]) class ChatResponse(BaseModel): """O que a API devolve no POST /chat.""" resposta: str agentes_chamados: list[str] = Field(default_factory=list) class SessionResponse(BaseModel): """Ainda não é usado — é do Passo 6 da Etapa 3.""" session_id: str resumo: str | None = None
Repare no session_id

No script era a constante "id_usuario" — um usuário, para sempre. Agora é um campo da requisição: cada mensagem diz a que conversa pertence. É isso que permite duas pessoas usarem o assessor ao mesmo tempo sem misturar históricos.

No chat.py, o dict vira os schemas:

Por que um arquivo só para isso

Num script, criar um modelo custa uma vez e ninguém percebe. Num servidor, o import roda uma vez e os objetos ficam vivos atendendo todas as requisições. Se cada arquivo criasse o seu, você teria conexões duplicadas e configurações divergindo sem ninguém notar.
